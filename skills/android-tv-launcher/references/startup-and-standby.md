# 启动、待机与 HOME

## 六个不同层次

| 层次 | 控制者 | 应用侧能证明什么 |
|---|---|---|
| 上电第一帧 | bootloader、面板或板级固件 | 应用截图无法证明已替换 |
| 系统启动动画 | 系统服务及其动画资源 | APK内部动画不等于该阶段 |
| Android默认HOME | 系统解析器、厂商策略 | 必须回读解析结果并实际按HOME |
| 厂商第三方启动入口 | 厂商桌面或服务 | 设置读回只是条件，需实际冷启动 |
| 应用内部开场 | 自己的Activity与渲染器 | 可测试可见时长、取消与首页衔接 |
| 遥控待机与唤醒 | 电源管理、进程清理、前台恢复 | boot_count通常不增加，需单独关/开测试 |

用户要求“开机就是自己的画面”可能涉及全部层次。交付时分别标注，不能用最后两层代替前四层。

## 冷启动入口

可复用做法是独立启动桥接，承担前台转交，不承担常驻全局监听：

1. 首次运行建立boot_count基线，避免安装后把当前会话误认作开机。
2. 新boot_count且处于合理启动窗口才申请一次开场；缺失计数或读取失败时不盲目启动。
3. 只在Activity已resumed且确实有窗口焦点时转交。
4. 等待首次焦点的期限用单调时钟定义。冷启动高负载时，焦点可能比onResume晚数秒。
5. 已获得焦点后失焦、onPause、超时、失败都取消；不在后台延迟抢回。
6. 消费标记与“开场确实呈现”是不同状态。过早消费能防重入，但可能在被打断后省略开场，应记录这项取舍。

把厂商INFO入口放进独立桥接任务，主应用只提供正常应用图标入口。某些系统的`getLaunchIntentForPackage`优先INFO；把INFO直接放在主应用可能吞掉用户正常点图标的启动，甚至把已有主任务意外带到前台。透明过渡窗口也须检查焦点、超时和失败落点，不能留下透明黑屏HOME。

示例桥接的窗口时限是保守起点，应在目标设备测量。HOME路由到桥接以后是否播放开场，应按新boot区分；普通HOME不重复播放。

## HOME命令表面成功，但仍进原生桌面

查看实际resolver、preferred activity、HOME role、系统日志以及系统是否限制第三方HOME。某些固件在目标包不是system app时直接拒绝设置，命令表面Success并不代表路由生效。

若系统阻止：明确报告缺口，保留原生桌面和能正常打开的应用入口。停用整个原生桌面可能同时破坏电视内容、设置/信号源或原生恢复流程，不能用它掩盖共存要求。不要加回全局HOME广播或观察原生窗口抢回桌面来伪装默认路由成功。

## 关机前是自有桌面，开机却是原生桌面

先比较boot_count与uptime，检查睡前、睡后、醒后的前台和应用停止状态。

- 计数不变，睡前系统主动START HOME，再force-stop第三方：优先查厂商待机保留/清理策略。
- 计数不变，前台保持但本应用崩溃：查生命周期与进程退出，不先改启动项。
- 计数增加，厂商入口没收到：查启动项及厂商条件。
- 入口收到但没有前台焦点：查窗口、等待期限与取消原因。
- 已转交又被其他活动覆盖：查明确的后续活动来源，避免重试循环。

### 小米固件的特定适配案例

曾观察到 `gotoSleepStayAliveProcess` 把非名单中的前台应用切回HOME，随后结束第三方进程。该样本代码在入口读取：

```text
Settings.Global.disable_back_home_whitelist == "disable"
```

匹配时退出这段“回HOME＋清理”处理。这是**某固件中已观察的行为，不是所有小米设备的公开保证**。脚本要求显式选择厂商适配并确认本机证据；不凭键名自动写入。

这项修改影响所有应用的该待机处理，效果是恢复睡前前台：自有桌面醒来还是自有桌面，原生App醒来还是原生App。它不会强制从任意原生播放回自有桌面，也不替换系统启动动画。修改前保存原值（包含“原来不存在”），修改后测自有和原生两条路径，具备撤回方法。

### 厂商启动项的另一条路径

某些固件使用`Settings.System.start_3rd_app`和第三方INFO入口，冷启动与STR唤醒可能共用一部分分支，还受广告、静默重启、输入源自动播放等条件影响。部分实现会把非空目标缓存到厂商私有偏好。公开键为空不一定代表无目标；恢复公开键也不必然抹除厂商缓存。若无法确认缓存恢复，明确保留未知，不能写“恢复全部启动行为成功”。
